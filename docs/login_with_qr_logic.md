# FadlPos: вход по PIN и зашифрованному blob (`get_qr_data` / `login_with_qr`)

Документация по API каскадного логина для POS/мобильных клиентов: выдача зашифрованного пакета с API-ключами и последующий вход по blob + PIN без повторной передачи пароля.

---

## Зачем это нужно

- Первичная привязка устройства: после проверки **логина и пароля** сервер генерирует/обновляет **API Key / API Secret** пользователя, упаковывает их в **зашифрованный blob** (ключ производится от **PIN**).
- Повторные входы: клиент хранит blob локально и отправляет **blob + PIN**; при успехе создаётся обычная сессия Frappe (**cookie `sid`**).

### PIN (код доступа)

**`pin_code` — ровно 6 цифр** (`0`–`9`), без пробелов и других символов. Иначе оба метода отвечают ошибкой аутентификации с текстом вроде «PIN must be a 6-digit code». Так зафиксирован единый формат для кассовых/мобильных клиентов.

---

## Почему нельзя использовать пользователя **Administrator** (и **Guest**)

В коде явно отклоняются учётные записи из **`frappe.STANDARD_USERS`**. В стандартном Frappe это кортеж **`("Guest", "Administrator")`**.

Причины:

1. **Системные учётные записи** не предназначены для типичного POS/кассового сценария; у **Administrator** особые ожидания по безопасности и аудиту.
2. **Guest** не является полноценным пользователем с паролем в вашем потоке.
3. Единообразие: каскад рассчитан на **обычных System User** с ролями вроде кассира/менеджера, а не на встроенного суперпользователя сайта.

Попытка вызвать `get_qr_data` с валидными учётными данными **Administrator** приводит к ответу с ошибкой аутентификации (тот же путь, что и при неверных учётных данных: `_bad_creds()`).

Используйте отдельные учётные записи (например `user@company.com`) с нужными ролями.

## Как это устроено

### Шифрование (`fadl_pos.api.login.pin_cipher`)

- Формат blob: префикс версии, **соль**, **nonce**, **AES-GCM** ciphertext.
- Ключ: **PBKDF2-HMAC-SHA256** от PIN и соли (итерации заданы в модуле).
- В plaintext JSON попадают **`api_key`** и **`api_secret`** (открытый секрет только до сохранения в ответе; в БД секрет хранится как поле типа **Password** в `__Auth`).

### `get_qr_data(login, password, pin_code)`

- **Whitelist:** только для **авторизованной сессии** (`allow_guest=False`).
- Проверяет логин/пароль через **`User.find_by_credentials`** (учитываются настройки: вход по email / username / телефону).
- Отклоняет отключённых пользователей и **`STANDARD_USERS`**.
- **Права на генерацию ключей:**
  - текущая сессия совпадает с целевым пользователем (**себе**), **или**
  - у текущего пользователя есть роль **System Manager** (тогда можно передать **чужие** `login`/`password` и выдать blob для этого пользователя — после проверки пароля).
- Обновляет **`api_secret`** (и при необходимости создаёт **`api_key`**), сохраняет User с **`ignore_permissions=True`** (доступ уже проверен в endpoint).
- Возвращает **`{"encrypted_blob": "..."}`**.

**Важно:** каждый успешный вызов **перезаписывает `api_secret`**. Старые blob для этого пользователя перестают работать с `login_with_qr`.

### `login_with_qr(encrypted_blob, pin_code)`

- **Whitelist:** **`allow_guest=True`** — вызывать можно без сессии.
- Расшифровка PIN → проверка пары ключ/секрет через **`validate_api_key_secret`** (как при `Authorization: token …`).
- **`LoginManager().login_as(user)`** — полноценная сессия, в ответе выставляется **`sid`**.
- Повторный логин без `logout` создаёт **новый `sid`**; старая запись сессии в БД может ещё существовать до устаревания — это нормальное поведение Frappe.

## API v1 и v2

- Ответы и ошибки **v2** структурированы иначе (`data`, `errors`, `messages`). Путь: **`/api/v2/method/<полный.путь.функции>`**.
- Классический путь: **`/api/method/<полный.путь.функции>`** (обрабатывается как **v1**).

**Вход в систему (логин/пароль):** эндпоинт **`POST /api/v2/method/login`** в Frappe **не выполняет аутентификацию** (заглушка). Чтобы получить cookie для вызова `get_qr_data`, используйте **`POST /api/method/login`** (v1) с телом `{"usr","pwd"}`.

Примеры методов (модуль `fadl_pos.api.login.login_with_qr`):

- `fadl_pos.api.login.login_with_qr.get_qr_data`
- `fadl_pos.api.login.login_with_qr.login_with_qr`

Заголовок **`Host`** должен соответствовать имени сайта (например `development.localhost`), если bench обслуживает несколько сайтов по одному IP.

## Тесты

Файл: **`fadl_pos/tests/test_login_with_qr_api.py`**.

Покрытие (**по 5 сценариев на эндпоинт**, интеграционные тесты, базовый класс **`IntegrationTestCase`**):

**`get_qr_data`**

1. Успешная выдача blob для себя (пользователь без System Manager), PIN из 6 цифр.
2. Неверный пароль.
3. Некорректный PIN (пустой, не 6 символов, не только цифры).
4. Нет прав: не-SM пытается выдать ключи по **другим** валидным учётным данным.
5. **Administrator** (System Manager) может выдать blob для другого пользователя по его логину/паролю.

**`login_with_qr`**

1. Успешный вход и установка сессии.
2. Неверный PIN (другие 6 цифр) или неверный формат PIN (не 6 цифр).
3. Пустой blob.
4. Порча blob.
5. После смены `api_secret` в БД старый blob отклоняется.

Запуск:

```bash
bench --site <ваш_сайт> set-config allow_tests true   # при необходимости
bench --site <ваш_сайт> run-tests --app fadl_pos
```

В тестах задаются **`set_request`**, **`CookieManager`** и **`LoginManager`**, иначе при прямом вызове `login_with_qr` не хватает контекста запроса, как в проде.

## Безопасность (кратко)

- Использовать только по **HTTPS** в проде.
- PIN фиксированной длины **6 цифр**; на стороне сервера стоит жёсткая проверка формата. Дополнительно имеет смысл ограничивать число попыток на IP/устройство.
- Blob = владение ключами; хранить как конфиденциальные данные на устройстве.
- Не передавать пароль и PIN в логах и в публичных репозиториях.
